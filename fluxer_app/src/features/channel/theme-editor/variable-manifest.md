# Channel Theme Variable Manifest

## What this is

Crawl output for piece 4a of the channel-themes feature. It is the reference the editor
controls are generated from: every custom property the app's own theme manifest declares,
with the default value it resolves to, how much it actually changes the look of a channel,
and which editor control fits it.

Nothing here is invented. Every variable, group and default value is read directly out of
`fluxer_app/src/features/theme/variables/ThemeVariableManifest.ts`; the gaps at the end are
each backed by a file and line number.

## How it was produced

`ThemeVariableManifest.ts` is a generated file (`scripts/GenerateThemeVariables.ts`) and
exports everything needed:

| Export | Used for |
|---|---|
| `THEME_VARIABLES` | the 333 variables, each with its `kind` and `groupLabel` |
| `THEME_STUDIO_DARK_DEFAULT_VARIABLE_VALUES` | the **dark** default column (the `:root` block) |
| `THEME_STUDIO_LIGHT_DEFAULT_VARIABLE_VALUES` | the **light** default column (`:root` overridden by `.theme-light`) |

Both artifacts were generated by importing those exports rather than transcribing them, so
the variable set is exhaustive by construction: **333 in the manifest, 333 emitted, none
missing a default value.** 145 of the 333 differ between light and dark; the other 188 are
identical in both and are shown as a single value.

**Categories** are the manifest's own `groupLabel` values, not a new taxonomy.

**Input type** is derived from the manifest's `kind`, with four deliberate overrides:

- `--font-sans`, `--font-mono`, `--font-keybind` → `font-family`
- `--link-decoration` (`none` | `underline`) and `--user-select` (`auto` | `none`) → `select`; these
  are the only two variables the runtime actually toggles between fixed values
  (`useThemeCssVariables.ts`)
- `--theme-border-width`, `--message-highlight-bar-width`, `--message-reply-spine-width` →
  `border-width`; these are the three tokens that are purely a line thickness
- the four `--button-*-outline-border` variables → `text`, not `border-width`: their values are
  full border shorthands (`1px solid <color>`), not a bare width

**Impact** is a judgement call, applied as: `high` = changes the channel's appearance at a
glance (surfaces, body text, the message row, the composer, radii, font); `edge-case` = rarely
visible, or **not reachable from a channel-scoped override at all** (app-shell variables,
`--z-index-*`, ANSI colors, markdown tables and alert callouts, premium upsell surfaces);
`medium` = everything else.

## Scope: what a channel theme can actually reach

The scoped style is injected onto the `<main>` element rendered by
`features/channel/components/ChannelLayout.tsx` (`containerRef` at L32-33, `ref` at L64), which
wraps `ChannelIndexPage` for all three channel routes (`app/router/routes/AppRoutes.tsx`
L242, L300, L321). CSS custom properties set on that element cascade to everything inside it.

**In scope, confirmed:** the message input area. `ChannelTextarea` is a plain JSX child of
`GuildChannelView` (L426, L440), which renders inside `ChannelLayout`. All 22 `Forms` variables —
including every `--textarea-*` token — are therefore reachable by the scoped injection, as are
the channel header, message list, and member list.

**Out of scope:** the app shell (server rail, channel sidebar, user area, titlebar, mobile
bottom nav) and everything rendered through `createPortal` into `document.body` (modals,
popouts, tooltips, toasts, bottom sheets). See gaps 13 and 14.

## Hardcoded gaps and scope limits

Things that are visually retheamable in principle but are **not** driven by a manifest
variable, plus manifest entries that cannot actually be reached from a channel-scoped
override. Flagged only — nothing here was fixed, per the crawl's scope.

1. Scrollbar geometry is hardcoded, not variable-driven. Only the three colors (--scrollbar-thumb-bg, --scrollbar-thumb-bg-hover, --scrollbar-track-bg) are tokens. In features/theme/styles/Scroller.module.css the track width/height is a literal 1rem (L10-13), the thumb min-height is 2.5rem (L21), the thumb/track inset border is 0.25rem solid transparent with border-radius 0.5rem (L42-47), and .scrollerWithBottomGutter adds a literal 0.5rem margin (L29). A channel theme can recolor the scrollbar but cannot resize or reshape it.

2. Avatar shape is not themeable. The circular crop is a literal border-radius: 50% in features/ui/components/BaseAvatar.module.css (L22, .overlay) and features/ui/avatars/AvatarStack.module.css (L24, L32). No avatar-shape token exists anywhere, so a channel theme cannot make avatars squared or rounded-rect. Only --message-avatar-size / --message-avatar-size-compact (size, not shape) are exposed.

3. Avatar status-badge and mask variables exist in CSS but are absent from the manifest. features/ui/components/BaseAvatar.module.css consumes --avatar-status-radius (L47), --avatar-mask-cx / --avatar-mask-x / --avatar-mask-width (L69-71), --avatar-status-right / -bottom / -width / -height (L40-45). These are never declared in any CSS file; they are written as inline styles from BaseAvatar.tsx (see the typed style keys at L40 and the assignment at L231). Inline styles on the avatar element beat an inherited channel-scope value, so overriding them from a channel theme would not work even if they were surfaced.

4. Avatar transition timing is hardcoded outside the manifest. --avatar-status-transition-duration (160ms) and --avatar-status-transition-easing (ease-out) are declared on the .container component class in features/ui/components/BaseAvatar.module.css (L5-6), not on :root, so the manifest generator never sees them. They also do not reuse --transition-fast/normal/slow.

5. The manifest generator only reads :root and .theme-light declaration blocks (scripts/GenerateThemeVariables.ts, readSourceVariables - it skips every block whose selector is neither, L174-179). Any custom property declared on a component class is structurally invisible to the manifest. This is the root cause of the avatar gaps above and is a general blind spot, not a one-off omission.

6. The manifest models only two themes, but four exist. features/theme/styles/generated/color-system.css defines :root (dark, L3), .theme-light (L190), .theme-coal (L324) and .theme-dark_legacy (L427). THEME_STUDIO_DARK/LIGHT_DEFAULT_VARIABLE_VALUES cover only the first two, so for a user on coal or dark_legacy the editor default shown next to a control will not match what they actually see.

7. --saturation-factor is inert when set at channel scope. Every color in color-system.css bakes var(--saturation-factor) into its own declared value on :root (e.g. --background-primary: hsl(258, calc(10% * var(--saturation-factor)), 5%)). Per the CSS custom-property spec, var() inside a custom property is substituted at computed-value time on the element the declaration applies to, so descendants inherit an already-substituted color. Overriding --saturation-factor inside [data-channel-theme-id] therefore affects only declarations written in that same scope, not the inherited palette. It is in the manifest but effectively a no-op for a channel theme.

8. --textarea-horizontal-padding has a malformed default value in the manifest: "1rem)" with an unbalanced closing paren (ThemeVariableManifest.ts L1166 and L1502). The real source is --textarea-horizontal-padding: var(--chat-horizontal-padding, var(--spacing-4)) (features/channel/components/textarea/TextareaInput.module.css L16). The generator regex for var() fallbacks is /var\(\s*(--[a-zA-Z0-9_-]+)(?:\s*,\s*([^)]+))?\)/g - the [^)]+ fallback group stops at the first closing paren, so a nested var() fallback is truncated and leaves a stray ")". This is the only malformed value of the 333 (verified by a paren-balance scan over both maps); the true runtime value is 1rem. An editor seeding a control from this default would emit invalid CSS.

9. --textarea-side-button-padding and --typing-upload-column-width use a unitless zero inside max() alongside lengths: max( 0, calc((2.5rem - 2.25rem) / 2) ). CSS math functions require consistent argument types, so a bare <number> against a <length> is invalid at computed-value time. This is the same bug class the repo already fixed elsewhere (commit dbe38255, "fix(app): unitless zero fallback in voice calc"). Source: features/channel/components/textarea/TextareaInput.module.css L19-22 and src/app/globals.css L115-118.
